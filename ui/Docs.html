Overview

What Emma is and what it does

Emma is a fully local AI chat system built on RAG — Retrieval-Augmented Generation. It lets you upload text documents and ask questions about them. The model answers using your documents as the source of truth, not its training data.

🔒
Fully private
All inference runs locally via Ollama. No API keys. No external calls. No telemetry.
📄
Document-grounded
Every answer is sourced from your documents. The model doesn't make things up from training data.
🔍
Semantic search
Finds relevant content by meaning, not keyword matching. Works across languages.
🏷️
Auditable responses
Every response is tagged [RAG], [DRIFT] or [NO INFO] so you always know the source.

Installation

Get Emma running in a few minutes

1. Install Ollama

Download and install Ollama from ollama.com/download. Then pull a language model:

ollama pull qwen2.5:7b

Verify it works:

ollama run qwen2.5:7b

2. Other recommended models

ollama pull mistral:7b      # Best for following format instructions
ollama pull llama3.2        # Lightweight, good instruction following
ollama pull deepseek-r1     # Slower but more precise reasoning

3. Clone and install

git clone https://github.com/yourusername/Emma-Chat.git
cd Emma-Chat

python -m venv .venv

# Windows
.venv\Scripts\activate

# Mac / Linux
source .venv/bin/activate

pip install -r requirements.txt
Note: The first run downloads the multilingual embedding model (~120MB). This happens automatically and only once, then stays cached locally.

Running Emma

Two servers, one command

Windows

run.bat

Mac / Linux

source .venv/bin/activate
uvicorn server:app --reload --port 8000 &
cd ui && python -m http.server 5500

Then open http://localhost:5500 in your browser.

How RAG works

Retrieval-Augmented Generation from scratch

RAG grounds the model's answers in your documents instead of its training data. Think of it like OOP inheritance — the document context (the child) overrides the model's general knowledge (the parent).

1
Routing
The LLM reads the list of available files with their auto-generated descriptions and selects up to three documents that are genuinely useful for the question. Comparative questions can use more than one RAG at once.
2
Semantic retrieval
The question is converted to a vector (embedding) and compared against all chunk vectors using cosine similarity. The top chunks from each selected document are gathered and labeled by source before being sent to the model.
3
Augmentation
The selected chunks are injected into the prompt as source-tagged context, along with strict rules about how to answer, compare documents when needed, and which tag to use.
4
Generation
The model answers using only the provided context. The server validates and corrects the response tag before sending it to the frontend.

Document indexing pipeline

When a file is uploaded, the server runs this pipeline automatically in the background:

1
Chunking
The document is split into paragraphs. Short paragraphs are merged until each chunk reaches a minimum of 40 words. Low-quality chunks (repeated lines, image references, digit-heavy content) are discarded.
2
Embedding
Each chunk is converted to a 384-dimensional vector using paraphrase-multilingual-MiniLM-L12-v2. Vectors are saved as a .npy file alongside the JSON index.
3
Description generation
The LLM reads the first 2000 characters and generates a one-sentence description. This is stored in files_index.json and used by the router to match questions to documents.
4
Inconsistency check
Before the upload completes, the server compares the new document against the user-visible RAGs. It uses embeddings to shortlist candidates and an LLM to flag likely contradictions such as conflicting percentages, dates, thresholds, or policy rules. Results are stored in conflicts_index.json and surfaced in the upload UI.

Response tags

Every answer tells you where it came from

Emma prefixes every response with a tag indicating the source of the answer. The server validates and corrects the tag if the model gets it wrong.

[RAG]
The answer is fully supported by the document context. The model used only your files to answer.
[DRIFT]
The context existed but was insufficient. The model supplemented with its own training knowledge. Treat this answer with more caution.
[NO INFO]
The question has no relation to any available document. The model answered from its own knowledge base.
Tip: If you see too many [DRIFT] responses, try increasing TOP_K_CHUNKS in server.py to retrieve more context per query.

Chunking functions

FunctionDescription
is_quality_chunk()Language-agnostic filter. Discards chunks with too few unique words, repeated lines, high digit density, or duplicated halves.
chunk_text()Splits document by double newlines. Merges short paragraphs until minimum word count is reached. Applies quality filter before saving.
generate_description()Sends first 2000 chars to LLM, returns a one-sentence description of the document.
save_description()Writes description to files_index.json. Never overwrites manually-set descriptions.
process_file()Full ingestion pipeline: chunk → embed → save JSON + NPY → generate description.
sync_files()Runs at startup. Processes any files in files/ that don't have a corresponding index yet.
detect_rag_inconsistencies()Shortlists similar documents and asks an LLM to find likely contradictions before persisting warnings to conflicts_index.json.

RAG functions

FunctionDescription
cosine_similarity()Computes dot product between normalized vectors. Score of 1.0 = identical meaning, 0.0 = unrelated.
retrieve_chunks()Vectorizes the question, computes similarity against all chunk vectors, returns top K chunks per selected document.
route_to_files()First LLM call. Given the file list with descriptions and the question, returns up to three relevant files instead of forcing a single document.
build_rag_prompt()Assembles the final prompt with source-tagged chunks so the model can answer or compare across multiple RAGs.
fix_tag()If RAG is active and the model used the wrong tag, replaces it with [RAG] before sending to the frontend.

API endpoints

All endpoints are served on port 8000

Health check

GET/health

Checks if Ollama is reachable. Returns status and list of available models. Used by the frontend to populate the model selector and show the connection indicator.

List files

GET/files

Returns all documents in files/ with their indexing status, chunk count, description, and any persisted inconsistency warnings.

Upload file

POST/upload

Accepts a .txt file via multipart form. Saves it to files/, runs inconsistency detection against visible RAGs, persists any warnings, and triggers the indexing pipeline in the background.

Download file

GET/files/{stem}/download

Serves the original .txt file for download.

Delete file

DELETE/files/{stem}

Removes all traces of a document: the .txt, the .json index, the .npy embeddings, and the entries in files_index.json and conflicts_index.json.

Chat

POST/chat

Main chat endpoint. Accepts a model name, message history, and stream flag. Runs the full RAG pipeline and streams the response back in text/event-stream format.

{
  "model": "mistral:7b",
  "messages": [
    { "role": "user", "content": "What is Baroque?" }
  ],
  "stream": true
}

Response format per chunk:

data: {"text": "Baroque is...", "done": false}
data: {"text": " a Western style", "done": false}
data: {"text": "", "done": true}

Managing documents

Adding, updating and removing knowledge

Adding a document

Open http://localhost:5500/upload.html, drag and drop any .txt file. The server processes it automatically — no restart needed.

During upload, Emma also checks the new RAG against the user's own documents and the visible global documents. If it finds likely contradictions, the upload page shows a warning panel and the indexed file keeps a persisted Conflicts badge.

Naming convention: Use underscores instead of spaces. solar_panel.txt not solar panel.txt. The upload endpoint sanitizes filenames automatically.

Updating a document

Delete the existing file from the upload page, then re-upload the updated version. The system re-indexes it completely.

Manual descriptions

The LLM generates descriptions automatically, but you can edit files_index.json manually. The server never overwrites existing descriptions — only fills in missing ones.

{
  "baroque": "Wikipedia article about the Baroque artistic style, 17th-18th centuries",
  "contacts": "Company employee directory with phone numbers, emails and departments",
  "solar_panel": "Technical documentation about photovoltaic solar panel systems"
}

File structure after indexing

files/
  baroque.txt          ← original document
chunks/
  baroque.json         ← chunk index with text
  baroque.npy          ← embedding vectors
files_index.json       ← routing descriptions
conflicts_index.json   ← persisted inconsistency warnings

Privacy

What stays local and what doesn't

Emma was designed from the start for use with sensitive data. The architecture ensures nothing leaves your machine:

🖥️
LLM inference
All model inference runs via Ollama on your local machine. No requests to OpenAI, Anthropic, or any external API.
📐
Embeddings
The sentence-transformers model runs locally. Your document content is never sent anywhere to be vectorized.
📁
Documents
All files stay in your local files/ directory. The server only reads them — never uploads or transmits them.
📊
No telemetry
No analytics, no usage tracking, no external calls of any kind. The server only talks to Ollama on localhost.
Good for: internal company documents, employee contacts, legal contracts, medical records, financial data, proprietary technical documentation — anything you wouldn't want on an external server.
